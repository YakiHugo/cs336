## RoPE versus NoPE

- The owner correctly predicted that causal visibility provides indirect order clues even
  without explicit position encoding. Refined the mechanism by layer: a first-layer final
  attention read is invariant to permutation of earlier token embeddings, while earlier
  representations encode different nested prefixes that later layers can compare.
- Added `positional_encoding=none` as a default-preserving NoPE configuration. RoPE remains
  the default, and the official suite stays **46 passed, 2 platform skips** with Ruff green.
- A controlled random-model probe compared `[A,B,C]` with `[B,A,C]`: final-logit maximum
  difference was `3e-7` for one-layer NoPE, `0.638` for two-layer NoPE, and `0.091` for
  one-layer RoPE. This directly localizes explicit versus inferred ordering.
- At peak LR `3e-3`, the 100-step NoPE validation curve was
  `9.250→4.566→4.084→3.907→3.825`, compared with RoPE's
  `9.249→4.668→4.012→3.722→3.589`. NoPE learns most local language structure but ends 0.236
  worse as explicit relative position becomes useful.
- Captured the scored curve at `notes/a1/figures/rope_vs_nope.svg` and drafted the writeup.
  Learning remains in progress pending an identical-repeated-token transfer check; the
  parameter-matched SwiGLU/SiLU ablation follows.
- The repeated-token transfer check exposed a real boundary gap. The owner expected NoPE to
  retain a small difference between the 3rd and 30th identical token. Corrected this with an
  induction: attention averages identical V vectors to the same output regardless of how many
  are visible, and residual/FFN layers preserve equality. Distinct boundary/content tokens can
  break the symmetry, but numerical noise is not usable position information. NoPE learning is
  review-pending rather than owner-confirmed; moving to SwiGLU versus SiLU.

## SwiGLU versus SiLU

- The owner immediately identified why equal `d_ff` is unfair: SwiGLU has three large weight
  matrices while the ungated SiLU FFN has two. Taught the handout's matched-width accounting,
  `3×D×(8/3D) ≈ 2×D×(4D) = 8D²`, and the gate as input-dependent multiplicative feature
  selection.
- Added a configurable ungated `SiLUFFN` while preserving SwiGLU as default. Official tests
  remain **46 passed, 2 platform skips**, and Ruff is green.
- Parameter audit: SwiGLU `d_ff=1344` has 2,064,384 FFN / 22,696,448 total parameters; SiLU
  `d_ff=2048` has 2,097,152 FFN / 22,827,520 total, only 0.58% more overall.
- Under identical training controls, SiLU validation was
  `9.269→4.999→4.248→3.932→3.782`, versus SwiGLU
  `9.249→4.668→4.012→3.722→3.589`. Since the worse model is slightly larger, the 0.192
  endpoint gap supports gating efficiency rather than raw capacity.

## OpenWebText main experiment (in progress)

- The owner correctly rejected the claim that a higher OWT loss or worse sample by itself proves
  training failure. OWT is more varied and higher entropy, the same 40.96M-token compute budget
  covers less of its distribution, and its 32K tokenizer changes the unit relative to TinyStories'
  10K tokenizer. Random-uniform baselines are correspondingly about `ln(32000)=10.37` and
  `ln(10000)=9.21`; cross-tokenizer raw per-token loss is not an apples-to-apples quality metric.
- Serialized the full OWT corpus with resumable boundary-parallel encoding. Train contains
  2,727,120,452 uint16 tokens (4.371 bytes/token); validation contains 66,401,098 tokens
  (4.367 bytes/token). Both output sizes exactly equal two bytes per token.
- A controlled 100-step check used the base architecture, effective batch 32, context 256, and
  fixed validation sampling. Peak LR `1e-3` reached validation `6.750`; `3e-3` reached `6.860`
  after a training-loss overshoot to `9.727` and gradient norm `8.57`, so `1e-3` was selected.
- Added exact gradient accumulation and chunked LM-head loss so the 32K vocabulary fits efficiently
  on MPS. Physical batch 16 x two microbatches preserves the batch-32 gradient and 8,192 tokens per
  optimizer update. Full and chunked/accumulated one-step updates agree within `1.7e-6` maximum
  parameter difference; the official suite remains 46 passed, 2 platform skips with Ruff green.
- Launched `runs/owt_full_1e-3`: same architecture and 5,000 optimizer iterations as TinyStories,
  200-step warmup, cosine decay from `1e-3` to `1e-4`. Through step 100, training loss fell
  `10.383 -> 7.172`, gradient norm was `0.42`, and throughput was roughly 5.6-6.4k tokens/s.
- The owner clarified that macOS low-power mode is an intentional global constraint. Audited reusable
  software/runtime levers instead of changing power policy. Added inheritable profiles in
  `training_profiles.toml`, explicit FP32/BF16/FP16 autocast configuration, safe opt-in precision
  changes on resume, consolidated GPU/CPU synchronization, and a `caffeinate -i` profile runner.
- FP16 was rejected: although faster, its gradient norm collapsed from `0.38` to `0.045` in the
  representative short test. BF16 retained FP32's loss and gradient trajectory while raising steady
  OWT throughput to about 10.3K tokens/s. On real data from the exact step-200 checkpoint, step-250
  BF16 loss was `6.29182` versus FP32 `6.29156` on the same sampled batch (difference `0.00026`),
  and validation was `6.12567`.
- Tested `PYTORCH_MPS_PREFER_METAL` and `PYTORCH_MPS_FAST_MATH` separately and together. An apparent
  combined speedup disappeared when test order was reversed—the default path reached the same speed
  after warm-up—so neither environment variable was adopted. The full OWT run resumed from step 200
  in `runs/owt_full_bf16` using the unified profile; official tests remain **46 passed, 2 skipped**
  and Ruff is green.
